# 모바일 5단계 흐름 및 Gemini 판매글 검증 (2026-11-15 KST)

## 변경 파일과 동작

- `app.py`: 시작 화면을 별도로 유지하고 사진 입력 → 분석·수정 → 처분 계획 → 최종 견적 → 판매 준비로 구분. 선택한 물품만 최종 가격 목록·참고 가치 합계·최종 CSV에 포함. 최종 탐지 이미지와 상세 목록·가격 설명은 펼쳐보기로 정리. 전문업체·나눔 목록, 판매글 편집·복사·다운로드는 판매 준비로 이동.
- `disposal_view.py`: 대상 체크·물품명·수량·처분 방식의 4열 `st.data_editor`. 전체 선택/해제 유지. 객체 ID 스냅샷으로 콜백을 연결하고 편집 리비전으로 오래된 변경 내역의 재적용을 방지. 해제한 물품과 초안은 세션에 보존. 삭제·묶음 변경 시 기존 `disposal.sync_states`의 보관 규칙 유지. 판매 준비 기본 표는 3열, 상세 정보와 CSV는 유지.
- `presentation.py`, `styles/fieldsignal.css`: 5단계 표시, 기존 색상 유지, 모바일 버튼과 표 폭 축소, 하단 버튼의 모바일 sticky 해제로 입력창 가림 완화.
- `llm.py`: 판매글에 JSON 응답 스키마 추가, 빈 응답 검사, 키 누락·인증·모델·429·서버 혼잡·형식 오류를 비밀값 없는 문구로 구분. 판매글 요청은 최대 2회(기본 모델→대체 모델)로 제한. 사진 탐지의 기존 모델·프롬프트·재시도 계획 유지.
- `tests/`: 상태·파싱·실패 보존 회귀 테스트와 5단계 브라우저 테스트 추가/수정. 기존 가격 테스트에서 환경 키에 따라 실시간 외부 검색이 개입하던 2개 호출을 `allow_live=False`로 격리. 운영 가격 공식·DB 조회 코드·CSV는 변경하지 않음.

## 실제 Gemini 호출

Codex의 `.venv/bin/python` 실행 프로세스에서 환경변수 존재와 `llm.get_api_key()` 조회 성공을 boolean으로 확인했다. 키 값은 출력하거나 저장하지 않았다. 사진 탐지와 판매글 모두 이 조회 함수와 공유 클라이언트를 사용한다.

- 설치 버전: Streamlit 1.67.0, google-genai 3.1.0, Pillow 13.0.0.
- 수정 전 판매글 함수: `gemini-3.1-flash-lite` 단일 요청 성공. 수량 2개·제조사·모델·연식·긁힘·구성품·희망가격을 반영한 제목/본문 반환.
- 수정 후 판매글 함수: 동일 모델 단일 요청 성공. 구조화 JSON 파싱·인덱스 검증 통과, 작동 여부 미확인과 희망가격 미정 유지.
- 실제 Gemini 요청 총 2회. 인증/모델 접근/텍스트 생성 성공. 이 두 요청에서 429나 서버 오류는 관찰되지 않음.

**원래 Streamlit 배포의 실패는 Codex에서 재현되지 않았다.** 모델명이 틀렸거나 키가 없었다고 단정할 증거가 없다. 기존 화면이 예외를 모두 동일한 문구로 가렸다는 진단상의 문제는 수정했다. 구조화 응답은 잘못된 형식의 가능성을 줄이고, 최종 사실 검증은 계속 수행한다. 배포 환경의 Secrets와 할당량은 Codex와 별개이며 실제 배포 성공을 의미하지 않는다.

기존 `sale_facts`와 `validate_draft`를 유지해 모델이 새 상태·구성품·가격을 만들어 넣지 못하도록 한다. 제목 후보와 사실 문장의 순서만 모델이 선택한다. 실패 시 현재 글과 기존 후보는 보존하며 재생성 성공 시에도 사용자가 적용해야 덮어쓴다. 판매글/탐지 프롬프트 파일은 변경하지 않았으므로 동일 사진의 프롬프트 전후 비교 대상은 없다.

## iPhone 업로드 진단

기존 업로더는 JPG/JPEG/PNG와 10MB 제한의 Streamlit 기본 단일 파일 업로더였다. 이번에 `accept_multiple_files=False`를 명시했다. 앱 CSS는 웹 화면만 제어하며 iOS 사진 보관함 네이티브 선택창의 완료 버튼을 직접 제어하지 않는다. 선택창에서 아직 파일을 넘기지 못하는 증상은 Python 이미지 해독보다 앞선 단계다. 현재 코드만으로 iOS/Streamlit의 특정 결함이라고 단정할 수 없다.

사진 입력 화면에 우회 안내를 추가했다: 앱 내부 브라우저 대신 Safari로 열기, 파일 앱에 저장한 JPG/PNG를 파일 선택으로 업로드, 카메라 촬영, HEIC는 JPG/PNG로 변환, 10MB 이하 준비. HEIC 지원을 새로 추가한 것은 아니다.

**물리적 iPhone Safari와 iOS 사진 보관함은 검증하지 못했으며, 완료 버튼 문제를 해결했다고 주장하지 않는다.** Chromium 모바일 에뮬레이션의 파일 전달 성공은 네이티브 사진 선택창 검증을 대신하지 않는다.

## 검증과 제한

- `python -m unittest discover -s tests`: 78건 통과. 가격 계산·근거·DB 갱신·연식·재고·회전·처분·판매글 모의 응답 및 Streamlit AppTest 포함.
- 별도 데스크톱 마우스/390px 터치 테스트: 박스 드래그·미탐지 물품 추가·초기화·이름 수정·박스 삭제 통과. 실제 앱 진입 화면 로컬 렌더링 통과(API 호출 없음).
- 문법 검사: `app.py vision.py llm.py disposal.py disposal_view.py presentation.py` 통과.
- 기존 업로드 워크플로: Chromium 1200px/390px에서 카메라 UI 진입, PNG 업로드, 모의 탐지, 물품명·제조사 수정, 5단계 이동, CSV 내려받기, 사진/수정 상태 왕복 보존 통과.
- 추가 브라우저 테스트: `tests/preview_mobile.py`와 `tests/browser_mobile.py`로 320/390/1280px의 같은 행 선택·방식 편집, 선택된 CSV, 전체 해제 0원, 전체 재선택, 판매글 생성·직접 수정·모의 실패·왕복 보존 및 페이지 가로 넘침을 검사. 합성 집기와 모의 판매글을 사용한다.
- `test_pipeline.py`는 사진 인자 없이 import/실행만 확인. 실제 매장 사진이 제공되지 않아 실제 사진 탐지 회귀는 미검증. 실제 카메라 하드웨어, 물리적 iPhone Safari, 배포 서버 Secrets/API, 실제 429/503 상황은 미검증(오류 분기는 모의 테스트).
- 상태는 기존처럼 현재 Streamlit 세션에 한정된다. 브라우저 새로고침/종료 이후 영구 보존은 제공하지 않는다.

## 재현 명령

```bash
.venv/bin/python -m unittest discover -s tests
.venv/bin/streamlit run tests/preview_workflow.py --server.port 8502
python tests/browser_workflow.py
.venv/bin/streamlit run tests/preview_mobile.py --server.port 8503
python tests/browser_mobile.py
```

브라우저 테스트는 Playwright와 `/usr/bin/chromium`을 사용한다. 서버는 각각 별도 프로세스로 실행한다. 실제 API 테스트는 자동 테스트에 넣지 않아 CI에서 과금 요청을 만들지 않는다.
