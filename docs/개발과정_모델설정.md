# 이어가게 개발 과정 · 모델 설정 기록 (발표 자료용)

> 작성 시작 2026-11-08. 단계마다 "무엇을 왜 했고, 무엇을 측정했고, 무엇을 바꿨는지"를 기록한다.
> 수치는 팀 노트북(i5-1340P, RAM 16GB, GPU 없음)에서 측정한 값이다.

---

## 0. 전체 구조

```
[사용자] 매장 사진 업로드 / 카메라 촬영 (휴대폰·노트북 브라우저)
   ↓
① Florence-2-base (로컬, CPU) ─ 물체 탐지: 라벨 + 박스
   · <OD> 일반 탐지
   · <CAPTION_TO_PHRASE_GROUNDING> 품목 사전 단어로 한 번 더 탐지 (선택)
   · 사전 탐지 박스 검증: 잘라낸 영역 <CAPTION> 에 품목명이 나오는지 확인
   ↓
② 코드 1차 필터 ─ 사람·건물 구조 제외 목록, 너무 작은 박스, 두 탐지의 중복
   ↓
③ Gemini (API) ─ 2차 판별: 판매 가능한 집기만, 한국어 품목명, 묶음·개수
   ↓
④ 코드 검증 ─ LLM 이 근거 박스(id) 없이 만든 품목 제거, 개수는 박스 수로 확정
   ↓
⑤ 화면 ─ 박스 그림, 수정 가능한 품목표, 참고 시세(시세표), 판매처 검색 링크
```

역할 분담 원칙 (주최 측 지침 "규칙은 코드로" 반영)

| 단계 | 담당 | 이유 |
|---|---|---|
| 물체 위치·라벨 | Florence-2 (비전 모델) | 사진 이해는 규칙으로 불가 |
| 사람·벽 제외, 중복, 크기 | 코드 | 결과가 항상 같아야 하고 테스트 가능 |
| 판매 대상 판단, 품목명 통일 | LLM | 라벨 수가 무한해 규칙으로 다 적을 수 없음 |
| 개수, 근거 확인 | 코드 | LLM 이 개수를 틀리거나 물건을 지어내는 것 차단 |
| 가격 | 코드 + 시세표 | LLM 은 가격을 지어낼 수 있어 숫자를 맡기지 않음 |

## 1. Florence-2-base 설정

| 항목 | 설정 | 이유 |
|---|---|---|
| 모델 | microsoft/Florence-2-base (0.23B, MIT 라이선스) | CPU 실행 가능, 탐지·캡션·OCR 을 한 모델로 |
| 실행 | CPU, float32, attention=eager | GPU 없음. flash_attn 은 CPU 설치 불가라 import 목록에서 제외 |
| 입력 크기 | 긴 변 1024px 로 축소 | CPU 시간 단축 |
| 생성 | num_beams=3, max_new_tokens=1024 | 기본값. 1024 토큰에 걸리면 `truncated` 표시 → "나눠 찍기" 안내 |
| TensorFlow | `USE_TF=0` | transformers 가 쓰지 않는 TF 를 불러와 기동이 약 25초 걸리던 문제 |

### 1-1. 품목 사전 탐지 (phrase grounding)
- `<OD>` 는 일반 물체 어휘라 "에스프레소 머신·제빙기·쇼케이스" 같은 업소용 장비를 놓칠 수 있다.
- 그래서 품목 사전 24개 단어를 넣어 한 번 더 찾는다 (`vision.py` 의 `VOCAB`).

### 1-2. 발견한 문제와 해결: 사전 탐지의 오탐 (테스트 기록)
- **현상:** 꽃 사진(Windows 배경화면)에 사전 탐지를 돌리자 `refrigerator`, `sink` 가 나왔다. 사전 단어를 억지로 사진에 맞추는 경향.
- **해결:** 사전 탐지 박스마다
  1. `<OD>` 결과와 같은 물체로 겹치면(IoU>0.5) 통과
  2. 아니면 박스를 잘라 `<CAPTION>` 을 생성하고, 품목명(또는 동의어)이 캡션에 있을 때만 통과
- **결과:** 같은 사진에서 `refrigerator` 박스의 캡션이 "a branch with white flowers against a blue sky" → 제외. `sink` 는 박스가 너무 작아 제외. 오탐 2건 → 0건.
- **비용:** 박스당 캡션 1회. 상한 12개(`MAX_VERIFY`).

### 1-3. 측정값 (꽃 사진 1장, 1024px)
| 설정 | 시간 | 결과 |
|---|---|---|
| `<OD>` 만 | 2.5초 | flower 3 |
| `<OD>` + 사전 탐지(검증 전) | 4.4초 | flower 3 + refrigerator, sink (오탐) |
| `<OD>` + 사전 탐지 + 검증 | 8.7초 | flower 3 (오탐 제거) |

→ 실제 매장 사진으로 재측정 필요 (TODO: 테스트 사진 세트 확보 후 재현율·시간 기록)

## 2. 코드 1차 필터 (`vision.code_filter`)

| 규칙 | 내용 | 이유 |
|---|---|---|
| 제외 목록 | person, man, woman, people, face, hand, head / wall, floor, ceiling, window, door, pillar, stairs, building / sky, tree, grass, text, shadow, light, reflection | 대표 단어만 둔다. 모든 단어를 적을 수 없으므로 나머지는 LLM 이 2차로 거른다 |
| 최소 크기 | 사진 면적의 0.3% 미만 박스 제외 | 잡음 |
| 중복 | `<OD>` 와 사전 탐지가 같은 라벨을 IoU>0.6 으로 둘 다 잡은 경우만 하나로 | 처음에는 같은 작업 안에서도 중복 처리 → 나란히 놓인 의자가 합쳐지는 문제를 테스트에서 발견해 수정 |

## 3. Gemini 설정 (프롬프트 엔지니어링)

### 3-1. 프롬프트 구조 (`prompts/item_filter_v1.md`)
1. **[규칙]** 역할(폐업 매장 집기 분류기), 남길 것, 제외할 것, 묶기, 사전 이름 사용, 애매하면 `uncertain`, 가격·브랜드 금지, JSON 만
2. **[품목 사전]** 시세표와 같은 한국어 품목명 25개 → 이름을 통일해야 시세표와 연결된다
3. **[출력 형식]** `items[name, count, source_ids, in_dictionary, uncertain]`, `excluded[label, reason]`
4. **[예시]** few-shot 2개 (사람·벽 제외 / 컵·케이크 제외, 화분은 uncertain)
- 생성 설정: `temperature=0.1`, `response_mime_type=application/json` (JSON 강제)

### 3-2. LLM 출력 검증 (`llm.validate`)
- 입력에 없는 id 를 근거로 든 품목은 버린다 → 사진에 없는 물건 추가(환각) 차단
- 개수는 LLM 이 쓴 숫자가 아니라 **근거 박스 수**로 다시 계산

### 3-3. 모델 선택 과정 (측정 기록)
| 모델 | 단순 질문 응답 | 집기 판별 응답 | 판별 결과 |
|---|---|---|---|
| gemini-2.5-flash | — | — | 신규 사용자 사용 불가 (404) |
| gemini-3.8-flash | 55.6초 | 48.6~66.0초 | 기준 |
| gemini-3.8-flash, thinking=low | — | 44.3초 | 동일 |
| gemini-flash-latest | 58.5초 | — | — |
| gemini-flash-lite-latest | 7.4초 | — | — |
| gemini-3.5-flash-lite | 8.9초 | — | — |
| **gemini-3.1-flash-lite (채택)** | **1.2초** | **1.7~2.7초** | 3.8-flash 와 품목·개수·제외 동일. 차이는 "쓰레기통" uncertain 표시 1건 |

- 판별 테스트 입력: 라벨 20개 (사람, 벽, 창문, 천장 조명, 컵, 케이크, 메뉴판, 종이타월, 의자 3, 테이블 2, 에스프레소 머신, 쇼케이스, 냉장고, 화분, 포스기, 그라인더, 쓰레기통)
- 결론: 이 작업(짧은 라벨 목록 분류)은 작은 모델로 충분. 응답 시간 약 25배 단축.

|---|---|---|---|---|---|
| **fp32, beams 3 (채택)** | 1,302MB | **1,760MB** | 2.4초 | 4.5초 | 기준 |
| fp32, beams 1 | 1,302MB | 1,741MB | 3.6초 | 2.9초 | 메모리 차이 거의 없음 |

- 전체 앱(Gemini 포함) 최대 약 1.83GB → 한도 2.7GB 안. 서버가 혼잡해 최소치만 주어지면 부족할 수 있음.
- bf16 은 메모리를 줄이지만 CPU 에서 연산이 느려 시연 불가 → fp32 유지.
- 배포 후 메모리 초과 오류가 나면: 배포판만 사전 탐지 끄기 → 그래도 안 되면 다른 배포처 검토.

## 10. 무료 서버 CPU 제한 대응 (2026-11-08)
- 현상: Streamlit Cloud 에서 "Your app has been throttled" (무료 CPU 사용량 초과로 일시 감속)
- 실제 카페 사진(683×512)으로 설정별 비교, 노트북 CPU:

| 설정 | 시간 | 탐지 결과 | 메모리 | 판단 |
|---|---|---|---|---|
| fp32, 일반 탐지만 | 2.7초 | 의자 8, 테이블 3 | 1.78GB | **채택** |
| 8비트 압축(quantize_dynamic) | 2.2~4.9초 | 의자 6, 테이블 2 (누락↑) | 2.43GB (원본+압축본) | 기각 |
| 사진 768px 축소 | 2.7초 | 동일 | 동일 | 효과 없음 (모델이 내부에서 768×768 로 변환) |
| + 전문 장비 한 번 더 찾기 | 약 21초 | 17개 유지, 8개 검증 탈락 | — | CPU 부담의 주원인 |

- 적용: "전문 장비 한 번 더 찾기" 기본 꺼짐(필요할 때만 켜기), 검증 상한 12→8, 같은 사진 재분석 방지
- 결과: 분석 10.6초 → 2.7초 (노트북)
- 검토 후 보류: ONNX 변환본은 생성 과정을 직접 구현해야 해서 해커톤 일정 대비 위험이 큼
